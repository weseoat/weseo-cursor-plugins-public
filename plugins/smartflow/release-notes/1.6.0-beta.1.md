# SmartFlow 1.6.0-beta.1

Feedback release from the 2026-09-25 triage: thirteen Confluence entries (eleven bugs, two ideas — reported 2026-09-19 to 2026-09-24 on plugin 1.5.0 at Wiener Zucker, Quality Austria, Hotel Hubertus) analysed in `plugin-feedback/` and implemented as five bundles in one beta build. One new always-on Rule (`runner-gate`, 23rd Rule); the two CSS QA Skills get an Execution Gate; ACF Local JSON gets its pull-before-deploy hook, the `modified` rule, and the clone/tab pattern; the WST Section workflow gets neutral start questions, the same-purpose rule, a foundation-confirmation stop, the mandatory preview-fixtures block, and the per-context four-source proof; the Jira Skills get the Working Tree Discipline and the optional ticket transition; the setup wizards get `--isolated`, the restart-and-verify rule, and the ACF-before-docs gate order.

Sources (all thirteen analysed in `plugin-feedback/`):

- Bundle 1 — ACF Local JSON: `acf-clone-conditional-logic.md`, `acf-json-admin-sync-guide.md`, `acf-json-modified-timestamp.md`, `acf-json-pull-before-deploy-hook.md`.
- Bundle 2 — WST workflow: `wst-section-workflow-classification-order.md`, `wst-section-workflow-preview-harness-usage.md`, `wst-shortcodes-deep-loop-runtime-proof.md`.
- Bundle 3 — Runner delegation: `frontend-section-qa-runner-delegation.md` (two Confluence entries, one closed as duplicate).
- Bundle 4 — Jira: `jira-batch-workflow-foreign-worktree-changes.md`, `jira-ticket-close-on-request.md`, `jira-ticket-workflow-visual-diagnosis.md`.
- Bundle 5 — Setup: `playwright-mcp-availability.md`, `setup-acf-json-before-auto-docs.md`.

Each feedback doc's "Umsetzung im Plugin" section names the exact files and text changes for its item.

## Added

- **New Rule `runner-gate`** (23rd Rule, `alwaysApply: true`, ~10 lines): the four runner-backed Skills — `wst-section-workflow` and `wst-new-post-type` (runner `wst-shortcode-implementer`), `frontend-section-qa` and `cpt-frontend-qa` (runner `cpt-visual-implementer`) — execute only inside their runner; the main chat prepares the record, spawns exactly one runner per Section or surface, and runs deploy pass and commit gate. Hard stop before the first CSS/WST/ACF write or Playwright call when the current agent is not the runner; explicit non-reasons for skipping the runner (loaded Skill text, material already in context, "nur Styling", prior main-chat work, "one leaf is enough"); re-route check after a context break with the current file state as runner input; prompt split for mixed requests. `agent-routing` (requestable) stays the detail source; the same non-reasons are mirrored in its Orchestration point 1. Two real runs without a single spawn (Wiener Zucker accordion and text-images-one) confirmed the open risk "zero runtime evidence for the always-on runner delegation" from the 2026-08-26 agent review — see the new promotion criterion in Notes.
- **`setup-acf-local-json` Step 8 — the pull-before-deploy pre-commit hook**, the implementation of the Rule's operating rule 1 that until now had no mechanism: bundled asset `assets/pre-commit-acf-json-pull.sh` (bash, placeholders `<child-theme>`, `<ftp-host>`, `<remote-dir>` with a placeholder guard; FTP credentials from the repo-root `.env` via `WSO_FTP_USER`/`WSO_FTP_PASSWORD` over netrc, never on the command line; per-key merge so server-side admin changes land in the tracked JSON before the commit; `modified` guard; `--dry-run`; `ACF_JSON_PULL_SKIP=1` escape hatch). Installed as repo-level `.githooks/pre-commit` with `git config core.hooksPath .githooks` and `.gitattributes` `.githooks/* text eol=lf`; recorded as `acf_json_pull_hook: active` and `ftp_acf_json_path` in `PROJECT-CONTEXT.md`. `setup-ticket-ready` Gate 1 activates an existing hook in a fresh clone.
- **`acf-local-json` Rule — three new sections**: "Clone Fields And Conditional Logic" (no `conditional_logic` on seamless clone fields; variant switches through a local tab field in exclusion form `!=` inside one group; clone source field keys never carry the source tab — with the Wiener Zucker Intro tab pattern as the reference), "Admin Sync — Hand-Over Text For Colleagues" (the fixed German block: collective sync in ACF → Feldgruppen → Synchronisieren, then one unchanged save per group, `Abbrechen` on a second hint; where the admin reads from), and a "JSON Conventions Checklist". The `modified` rule becomes explicit: the real current UTC epoch via `python -c "import time; print(int(time.time()))"`, never a computed value or a value from the future (a future `modified` makes the admin sync hint permanent); `Get-Date -UFormat %s` is named as the forbidden PowerShell shortcut. Verification boundary `implementation pass, backend check by colleague pending` for structural JSON changes.
- **`section-preview-harness` — "Two jobs", "Harness state detection", and the sub-workflow "Configure a further Section"**: bootstrap and per-Section use are separated. Three states from three sources (key `section-preview-pages`, harness PHP file, real exporter config with `source_page != 0`): missing = offer; active = mandatory fixtures per Section; declined = skip. Files present without the key mean active — write the key and report it; there is no fourth state "files exist, so neither offer nor use". The sub-workflow runs exporter config → HARD STOP backend review → export over the route → preview URLs into the work record, main chat only, without a bootstrap stop. The key line `section-preview-pages: active` becomes a completion-checklist gate.
- **`wst-shortcodes` — "The proof is per form × nesting context" and "Known runtime constraints (verified in projects)"**: context classes `flat`, `loop-1`, `loop-2+` (nested loops or shortcode content inside another shortcode's content); a flat precedent or render proves nothing for `loop-2+`. Result vocabulary `proven` / `proven except runtime (<context>)` — the latter is a named runtime risk for work record, runner `GATES`, and deploy hand-over ("erster Deploy ist der Runtime-Test"), never a pass. Three settled constraints with project, date, and WST version (Quality Austria 2026-09-24, WST 6.19.x): (a) `wst_string_replace` cannot manipulate dynamically resolved content in `loop-2+` — use `wst_acf_number decimals=` / `wst_number_format`; (b) `[wst_variable]` getters in deep-loop shortcode content return empty, `{{$var}}` resolves before the SET; (c) `{{loopname}}` without a field is invalid, the loop post ID is `{{post_id/loopname}}`. `wst-nested-shortcodes` gets a one-line cross-reference under Common Failures.
- **`deploy-and-branches` — "Working Tree Discipline"**: the agent never discards, restores, stashes, or cleans uncommitted changes it did not make in this run; unexpected files are reported by path against a `git status --short` baseline, never staged or touched; a discard needs an explicit file-naming user confirmation; runners revert only their own edits inside their write scope and list reverted edits. Propagates into every worker prompt (`agent-routing` point 2) and into the integration check (`agent-routing` point 7).
- **Optional ticket transition on request** (`jira-ticket-workflow`, `jira-batch-workflow`): intake question in German, yes/no, default no („Tickets nach Review-Freigabe auf Fertig setzen?" — in the batch recorded as `transition: ja | nein` in the board header and read on resume). On yes: after review release and after the solution comment, read `jira_get_transitions` and pick the transition whose target status is in the **Done** category (name project-dependent, never guessed); exactly one candidate → execute, several → ask once, none → report and leave open. Only commented tickets are transitioned; `implemented`-without-commit, `blocked`, `route-back`, `skipped` never; the legacy "master — user commits" state behaves the same. Hard-rule text in both Skills: "Never transition ticket statuses unless the intake answer was yes; then only after review release, only for tickets that received a solution comment, only via the Done-category transition read from `jira_get_transitions`." The `jira-ticket-runner` stays transition-free.

## Changed

- **`frontend-section-qa` and `cpt-frontend-qa` restructured around an Execution Gate**: a new first section "Execution Gate (read first)" addresses the main chat (ensure or create the work record; spawn exactly one `cpt-visual-implementer` — per surface in the CPT Skill — with Skill name, Section/surface, record path, CSS scope, proof mode, QA profile, and on resume the current file state; stop until return; integrate, deploy pass, commit gate) and lists the non-reasons for executing in the main chat. Everything from the marker "Runner execution (`cpt-visual-implementer` only)" to the discrepancies section is runner-only; "Main chat again" resumes at the deploy pass. The workflow checklists are split into Main chat / Runner / Main chat blocks and the deploy step now names the user's commit confirmation. QA semantics unchanged. `frontend-section-qa` Required Starting Point: `Preview URLs` must be real `/section-preview/…` addresses or `n/a (declined)` / `n/a (no harness)` before the run starts — `<unresolved: …>` with an active harness is a hard stop with a route back to the fixtures sub-workflow, never a silent shift onto the test page. Preflight step 3 points at the new troubleshooting ladder of `playwright-browser-claim`; the stale "Step 10" references become "Step 11".
- **`cpt-visual-implementer` — "Inputs you accept"**: fresh start, **Resume with current file state** (a half-finished CSS file from the main chat is read, verified injection-proof, and continued — never restarted, never discarded unverified; inherited rules are listed as "inherited, verified/corrected" in `OWN CHANGES`), and the agent-routing handoff file. The agent follows only the runner part of the Skill.
- **`wst-section-workflow` — classification and remodel** (`classification-order` doc): the start question block asks three neutral questions (purpose, target page/place, design source) and no longer suggests a slug; the same-purpose rule makes an existing Section that serves the same purpose a remodel (`existing-section-remodel`), never a parallel new slug; a new "Foundation confirmation block" (keep/remodel, protected artefacts) is a mandatory hard stop before the first tracked write; `existing-section-remodel` gets its own compact checklist analogous to the foundation (discovery, execution plan, protected artefacts, ACF JSON change with real `modified`, deploy pass, served check, test content, preview line, Visual QA Targets, QA Brief); Example D covers the same-purpose case. The runner returns `OPEN DECISION: foundation not confirmed` when the confirmation is missing from its assignment.
- **`wst-section-workflow` — preview harness**: the three-state table from `section-preview-harness` replaces the key-only lookup, and the new block "Preview fixtures for this Section (mandatory when the harness is active)" runs the sub-workflow before frontend QA (exporter config in the main chat, HARD STOP backend review, export, preview URLs into the record). The visual-only route now reads "spawn the `cpt-visual-implementer` with `frontend-section-qa`" and references the `runner-gate` Rule. Checklist lines: "every new WST shortcode form four-source-proven per nesting context; `proven except runtime` is named in the deploy hand-over" (also in `wst-new-post-type`). `reference.md` gains "Variant switch on clones: the tab pattern (JSON)" and the `<unix-timestamp>` placeholder text now names the real-UTC rule.
- **`wst-shortcode-implementer`**: harness files stay off-limits (bootstrap and exporter config) but the runner returns `OPEN DECISION: preview-offer` for a missing harness and `OPEN DECISION: preview-fixtures` for a Section without fixtures in an active harness — it never skips the preview path because the files already exist. Form-choice rule when source 4 is unreachable before the deploy: least runtime dependency (self-formatting shortcode over `wst_string_replace`, field key over field name for imported data, direct field access over `wst_variable` indirection), riskier form named as alternative in the work record, `GATES: four-source: proven except runtime (<context>)` instead of `passed`.
- **`agent-routing`**: Deliberately Not Routed distinguishes `OPEN DECISION: preview-offer` and `preview-fixtures` and forbids orchestrator prompts that tell a runner "do not touch the harness" unless `section-preview-pages: declined` is recorded; Orchestration point 1 carries the non-reasons list and the prompt split; point 2 names the Working Tree Discipline as a worker constraint; point 7 adds the `git status --short` check against the run baseline (unexplained changes reported, asked from the plausible leaf via `resume`, never discarded).
- **`jira-batch-workflow`**: intake takes the `git status --short` baseline into the board header (a dirty start is not a blocker); step 5 handles unexpected files against the baseline (user work → leave and mention; new and unexplained → do not stage, report, ask the runner via `resume`; never `git restore`); the closing summary reports what was deliberately left untouched; spawn prompts carry the Working Tree Discipline. `jira-ticket-workflow` step 7 stages only the ticket's files and reports foreign changes by path.
- **`jira-ticket-workflow` — visual diagnosis** (`visual-diagnosis` doc): step 3 requires the before-measurement of target and reference on the served DOM for comparison tickets („gleich breit wie", „wie im Intro") — walk up from the visible box to the element that carries the property — and a one-sentence acceptance criterion (element, property, target value, viewport) that step 5 re-measures; "Regel angewendet" is not a pass. Ambiguity between two readings is asked once with both readings and a recommendation, never guessed. Step 4: existing project utilities and Section modifiers before new rules; a user-named fix direction is binding (deviate only with a reason and a question back). `jira-ticket-runner`: mandatory first step 4 (measurement and acceptance sentence), emergency brake extended with "ambiguous intent" (`OPEN DECISION: ambiguous intent`), reverts only its own edits, `OWN CHANGES` lists every touched file including reverted edits, `EVIDENCE` carries measured before/after values, `GATES` adds "foreign changes untouched".
- **`playwright-browser-claim` becomes the browser availability Rule** (`alwaysApply: true` unchanged, so it now covers every browser use, single-server setups and the `jira-ticket-runner` included): new section "Availability Check And Troubleshooting (single server too)" — (1) namespace check via `GetDynamicTools` before the first browser call; an absent namespace is a **deregistered** server after an `mcp.json` change → manual restart under `Settings` → `Tools & MCP`, never "loading", never a silent fallback; (2) "Browser is already in use" / `SingletonLock` → read the PID, check for an orphaned Chromium, present the evidence and ask before ending the process; `--isolated` as the durable fix; (3) `Timeout waiting for bubble creation` / `Failed to find tool call context` — even when shown as `User rejected MCP` — is a transient Cursor error: two retries with a pause, then report, no question round; (4) no substitute browser (`cursor-ide-browser` never sets a pass); (5) Node 18.17 floor. The claim/release protocol for `playwright-a/b/c` follows unchanged.
- **`setup-local-project`**: Step 11 template `"args": ["-y", "<playwright-mcp-package>", "--isolated", "--browser=chromium"]` with the one-sentence rationale (in-memory profile, no lock file, every server start clean; persistent `--user-data-dir` per workspace only when a project needs logged-in sessions, with the orphaned-process warning), Node 18.17 as a blocker; the change-and-restart rule — every `.cursor/mcp.json` edit ends with a manual restart under `Settings` → `Tools & MCP` **and** a namespace re-check — stated in Step 11 and as a general note in Steps 5 and 12. **Steps 14 and 15 swapped**: Step 14 = "Set Up ACF Local JSON" (gate `acf_local_json`, hand-over with the Rule's admin-sync text), Step 15 = "Generate The Docs Layer (First auto-docs Run)" (gate `docs_layer`), because `auto-docs` documents field groups and field tables from `acf-json/` — without it the first docs run writes `unbekannt` fields and a `field-groups/` `todo`. Fallback when the ACF gate ended `pending`/`skipped`: `docs_layer: done (field-groups pending: rerun auto-docs after acf_local_json)`; projects set up before this ordering resolve their `unbekannt` fields with one second `/auto-docs` run. Step 13 status list, Final Verification, and the frontmatter description follow the new order. `setup-ticket-ready`: Gate 6 uses the same template and restart rule; the Deliberately Out list names ACF before docs; Gate 1 activates an existing `.githooks/pre-commit`. `auto-docs`: a missing `acf-json/` on a SmartFlow project is named as the open ACF Local JSON gate with `unbekannt` markers and a `field-groups: todo (rerun auto-docs after acf_local_json)` index note, never as a final state. `project-template/PROJECT-CONTEXT.md`: gate rows reordered (`acf_local_json`, `acf_json_pull_hook`, `ftp_acf_json_path`, `docs_layer`), `section-preview-pages` row added.
- **`setup-acf-local-json`** Steps 4.2/4.4 (real UTC `modified` on the seed), 5.1/5.2 (`ftp_acf_json_path` recorded), Step 7 (hand-over with the Rule's admin-sync text; verification boundary), Failure Handling (permanent sync hint = future `modified`, fixed by setting the hits to *now*, never "old value + 1"; hook "cannot list" = chroot path variant) and completion checklist updated; `wst-new-post-type` and its `reference.md` carry the `modified` placeholder text and the seamless-clone bullet.
- Manifest descriptions updated for `acf-local-json`, `deploy-and-branches`, `agent-routing`, `playwright-browser-claim`, `setup-local-project`, `setup-ticket-ready`, `setup-acf-local-json`, `wst-section-workflow`, `section-preview-harness`, `wst-shortcodes`, `frontend-section-qa`, `cpt-frontend-qa`, `auto-docs`, `jira-ticket-workflow`, `jira-batch-workflow`, `wst-shortcode-implementer`, `cpt-visual-implementer`, `jira-ticket-runner`; the Rule count rises from 22 to 23.

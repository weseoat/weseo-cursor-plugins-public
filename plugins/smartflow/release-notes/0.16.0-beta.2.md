# SmartFlow 0.16.0-beta.2

Fix from the first live validation (WP Grid Builder 2.3.2): the single-item GET of the WPGB bridge routes hard-required the `Admin\Export` class, which WPGB 2.x removed — bridge 1.1.0 answered 501 on `GET /wpgb/<type>/<id>` there while list and save worked. Bridge template **1.1.1** adds the WPGB 2.x fallback; the canonical template is bumped so the mandatory version comparison rolls the fix forward instead of rolling a fixed project back to the broken 1.1.0 GET.

## Changed

- **Bridge template 1.1.1** (`install-status-bridge`): the single-item GET keeps the exporter branch on WPGB 1.x (class and method probed, no longer hard-required) and otherwise reads the row through `Database::query_row([ 'from' => <type>, 'id' => <id> ])` — the same documented internal the save path already relies on, never raw SQL. Empty/false rows answer 404. New helper `wso_bridge_wpgb_decode_json_columns()`: `settings`/`layout` are JSON-decoded only when they decode to arrays (non-JSON strings stay untouched); `css` is never decoded, because `save_row()` re-encodes only `settings`/`layout` and a decoded `css` would break the GET -> POST round trip. Response shape is unchanged (`{ wpgb_version, type, id, <type>: [row] }`), so POST keeps accepting the GET body. The file header now describes the 1.x/2.x split instead of listing `Admin\Export` as a required internal.
- `status-bridge` Rule: the WPGB single-item GET requires **>= 1.1.1 on WPGB 2.x** (1.1.0 list/save keep working; 1.1.0 GET 501s there). A 501 naming `Admin\Export` on a 2.x install means "bridge is 1.1.0" — the fix is the managed-block update through `install-status-bridge`, never a hand-edit or a project-only fork. New data-shape discipline from the live run: create payloads are cloned from a GET of a working item, never built from invented column sets (2.x grids have no `layout` column, cards carry `css`); grid card references and `grid_layout` facet references are **string ids** (`cards.default = "10"`, facets `"7"`), never slugs; the built-in carousel slugs `prev-button`/`next-button`/`page-dots` are not facet rows; `css` is posted back exactly as received.
- `wpgb-specialist`: the bridge-write gate rises to **bridge >= 1.1.1**; the create workflow carries the string-id note. The second gate (project-validated entry in `PROJECT-CONTEXT.md`) is unchanged.
- `install-status-bridge` Skill and `wst-new-post-type`: version references updated (wpgb/* since 1.1.0, the 2.x GET fallback since 1.1.1).

## Notes

- Live proof on `anton-llm-playground` (WPGB 2.3.2, bridge 1.1.1 as project-side fix): update round trip, card create by cloning (`wso-card-bridge-test`), facet creates with reindex (`bridge_test_checkbox`, `bridge_test_pagination`), and a grid create wiring the new card and facets by string id all passed. The open WPGB write-route validation is closed as validated in `docs/open-validations.md`.
- On a WPGB 2.3.x site with bridge 1.1.1 the acceptance checks are: `GET /status` reports 1.1.1; `GET /wpgb/grids/<id>` answers 200 with `settings` as an object; the GET payload POSTs back (200, `created: false`); cloned card/facet/grid creates answer `created: true` with new ids and matching re-reads; facet creates are followed by `POST /wpgb/reindex`.

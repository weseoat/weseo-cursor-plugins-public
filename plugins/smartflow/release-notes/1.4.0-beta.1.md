# SmartFlow 1.4.0-beta.1

Support colleagues can now bring an unprepared project to a **ticket-ready state in minutes** instead of running the full 13-gate setup wizard first. The new `setup-ticket-ready` Skill is the lite setup track of `setup-local-project`: only the six gates without which no support ticket works, everything else recorded as `pending` instead of skipped silently. `jira-ticket-workflow` gains a step 0 gate check that routes open gates there automatically — the colleague only pastes the ticket link.

Source: Confluence Skill-Einreichung `[Skill] setup-ticket-ready` (page 1971191811, grill-me decision log 2026-09-03). Proof case: Fandler [WP-42325] — a two-point fix (WPGB facet clone, placeholder, one accordion item, two CSS rules) that took less time than the setup before it, ending in a hard blocker because the project deploys `master` over WP Pusher where the agent may not commit.

## Added

- **`setup-ticket-ready` Skill** (new): resumable lite wizard in the same `PROJECT-CONTEXT.md` schema as `setup-local-project`. Six mandatory gates: (1) repo cloned at wp-content level, folder = server hostname; (2) `.env` plus REST test with `manage_options`; (3) minimal `PROJECT-CONTEXT.md` (URLs, theme path, deploy path as a fact, Jira site URL and project key, working branch); (4) working branch resolved, including the legacy state; (5) Atlassian MCP running with **Jira as the blocking surface** (ticket fetch, screenshots, comment — Confluence stays on-first-need); (6) Playwright MCP running. On-first-need gates recorded as `pending: on first need` and set up the moment a ticket needs them: status bridge, Figma MCP, Confluence anchor. Consciously excluded, recorded as `pending: Voll-Setup`: git-installer configuration, read-only FTP, options REST exposure, `.wso-deployed-commit`, `css_setup` marker — `setup-local-project` resumes exactly there, no break between the tracks.

## Changed

- **`jira-ticket-workflow`**: new step 0 gate check before intake — missing `PROJECT-CONTEXT.md` or open mandatory gates route to `setup-ticket-ready` (only the open gates), then the run continues; the gate check never forces the full wizard. Step 5 verification gains the **marker-based served check** for projects without a bridge or with `deployed_commit: null`: remember one unambiguous marker the fix introduces, check the served file after the push, missing marker → page cache → colleague flushes in the admin → re-check; reported honestly as marker-verified served, never bridge-verified. Step 7 closing: in the legacy `master — user commits` state the agent prepares the commit and hands over instead of committing; the Jira solution comment follows the support standard — no addressee, simple language, informative, calm; what was, what is different, page link, what is pending; commit hash and file paths go to the work record, not the ticket.
- **`deploy-and-branches` Rule**: `Working branch: master — user commits` is a recognized recorded state, not a per-ticket contradiction stop. In this state the agent never commits — it prepares (staged files, summary, proposed message with trailer) and the colleague commits and pushes. All other protections (no merge, no revert, no push, no branch creation) stay in force.
- **`setup-local-project`**: points support-only work to the lite track up front and resumes lite-prepared projects at their `pending: Voll-Setup` markers.
- **`agent-routing`**: `setup-ticket-ready` joins the deliberately-not-routed setup wizards (interactive main-chat Skill).

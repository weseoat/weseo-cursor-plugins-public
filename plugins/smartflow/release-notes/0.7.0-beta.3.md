# SmartFlow 0.7.0-beta.3

Setup now treats Atlassian MCP and Figma MCP as first-class gates, the same way it already treats Playwright MCP: the wizard checks whether each server is actually running in this Cursor session, not only whether a settings entry exists.

## Changed

- `setup-local-project` verifies **Atlassian MCP as Step 5**, before `weseo-git-installer`. The Confluence live read is a `confluence_search` (no baked-in page ID). Jira is noted in the same probe. User-level OAuth (`user-atlassian`) is preferred; credentials never go into `.cursor/mcp.json` or `.env`. Recorded as `atlassian_mcp: ready` or `pending: <reason>`.
- The git-installer step (now Step 6) **finds the current Confluence guide via `confluence_search`** (`weseo-git-installer` in space `Frontend`) and follows that page. No page ID and no parallel install recipe live in the Skill. Ambiguous hits are listed for the user; zero hits is a stop and ask for the URL. SmartFlow overlays stay in the Skill: child-theme target directory, `.wso-deployed-commit`, the agent never pushes. LastPass / Bitbucket API keys stay in the WordPress admin. `PROJECT-CONTEXT.md` records `git_installer_guide` as the page found this run.
- Figma MCP is a separate later gate (Step 11): catalog probe plus `whoami`. Do not call `get_design_context` during setup. Recorded as `figma_mcp: ready` or `pending: <reason>`; account email and handle stay out of `PROJECT-CONTEXT.md`.
- Playwright MCP moves to Step 10; filling `PROJECT-CONTEXT.md` to Step 12. Cross-references in `frontend-section-qa`, `cpt-frontend-qa`, and `migrate-ssh-to-local` are renumbered.

## Notes

- Atlassian is early because the git-installer walkthrough and its current status are maintained on Confluence, not in the plugin. Wave-2 Jira ticket workflows are not in this build.
- Figma is required for Section and CPT design reads in wave 1; the old Remote-SSH `setup-orientation` already treated it as a gate, and this restores that check in the local SmartFlow wizard.

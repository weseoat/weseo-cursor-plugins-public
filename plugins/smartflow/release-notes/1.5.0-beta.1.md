# SmartFlow 1.5.0-beta.1

Feedback release from six Confluence entries (one bug, four ideas, one rule submission — reported 2026-09-09 on plugin 1.4.1): `setup-local-project` gains the Confluence-guided FTP step with a verify CLI, the active Rovo keep-or-switch question, and two closing setup gates (docs layer, ACF Local JSON); every automatic Jira comment now ends with a SmartFlow signature line (new Rule); the WPGB facet shortcode is documented as the integration path outside the grid; and `deploy-and-branches` allows a push on a non-protected branch after an explicit per-request user instruction.

## Added

- **New Rule `jira-comment-signature`** (22nd Rule, `alwaysApply: true`, built like `commit-trailer`): every automatically created Jira comment — solution comments, transition/occurrence notes, worklog comments over `jira_add_comment` and `jira_edit_comment` — ends with its own last line `– erstellt mit SmartFlow` (signature wording decided by the maintainer). Never appended twice; Confluence comments are excluded (they keep their own intake format). `jira-ticket-workflow` (solution comment step) and `jira-batch-workflow` (batch solution comments) reference the Rule.
- **`setup-local-project` Steps 14 and 15 — the two closing setup gates**: Step 14 runs the first `auto-docs` pass to establish the project `docs/` layer (allowlist `.gitignore` release `!/docs/` `!/docs/**`, work records plus indexes, element docs deferrable to a marked follow-up run), gate `docs_layer: done | pending: <reason>`. Step 15 routes to `setup-acf-local-json` while both preconditions from this wizard are in place (bridge Step 9, FTP Step 8), gate `acf_local_json: done | pending: Export fehlt | skipped: <reason>` — `skipped` only after an explicit user decision, never silently. Both gates appear in Step 13's status list and as new Final Verification lines; `setup-ticket-ready` lists both in its `pending: Voll-Setup` set; `project-template/PROJECT-CONTEXT.md` carries the gate rows.

## Changed

- **`setup-local-project` Step 8 rebuilt on the Step 7 pattern**: the read-only FTP user is created from the live Confluence SOP, not from a baked-in recipe — `ftp_guide` ID from `PROJECT-CONTEXT.md` first, otherwise `confluence_search` in space `Frontend` for `ftpaccess` / `FTP Zugang einschränken` (one hit: follow; several: list and ask; none: stop, never invent steps). The role split resolves the SSH-vs-"no server shell" conflict explicitly: **creating** the user follows the Confluence SOP over the hosting main login (SSH/`nano`, executed by the user at their own terminal, credentials never in chat or `.env`); **verifying** runs from the workspace over the new read-only user via FTPS with a curl CLI analogous to the REST test (listing, known-file download, upload probe from `tmp/` that must be rejected, env vars only). The `.ftpaccess` block stays only as fallback when the found page does not show it. `PROJECT-CONTEXT.md` records `ftp_guide` (ID, URL, title as found this run) next to `ftp_read_access`; Step 13 and the Final Verification follow.
- **`setup-local-project` Step 5 detects a Rovo server and puts the switch to the user**: server classification by tool names (community `confluence_search` vs. Rovo `searchConfluenceUsingCql`); a found Rovo server triggers the active keep-or-switch question **before** the health check, with a one-sentence rationale (full tool surface incl. labels/attachments; version floor >= 0.22.0 reflects the audited security state). The answer lands in the `atlassian_mcp` gate as `server: community` or `server: rovo (kept by user)`. The existing second trigger (offer the switch when a Rovo-only workspace hits a missing capability) stays.
- **`deploy-and-branches`: "The Agent Never Pushes" becomes "The Agent Never Pushes (By Default)"** — adopted as submitted (rule submission page 1982595074): a push is allowed when the user explicitly instructs it in the current chat for the exact commit/branch at hand; the exception never applies to `main`/`master`/`trunk` (push-forbidden even with instruction); it is per request, never a standing mandate, and never carries over to later commits; the default hard stop and hand-over stay unchanged. After an instructed push, the same bridge verification runs as after a user push. Consistency: `commit-trailer` says "never pushes unprompted", the `jira-batch-workflow` hard rule references the Rule's push exception (the batch mandate never covers a push), manifest assumption and Rule description updated. Subagent workers stay push-banned entirely; the skill hard-stop sentences ("the agent never pushes") keep describing the default.
- **`wpgb-specialist` documents the facet shortcode**: facets are not restricted to the grid layout — `[wpgb_facet id="<facet-id>" grid="<grid-id>"]` renders a facet in Sections, sidebars, and templates; facet ID and grid ID are the two integration values and belong in the work record. The same note sits in the `status-bridge` Rule's WPGB write discipline (`grid-cards` describes no facet creation, so it stays unchanged).
- Manifest descriptions updated for `setup-local-project`, `setup-ticket-ready`, and `deploy-and-branches`; the Rule count rises from 21 to 22.

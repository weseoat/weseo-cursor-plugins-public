# Code Cleanup

Run this Skill to keep agent-written child-theme code small, consistent, and readable over time: it removes leftovers, aligns code with the project's conventions, folds duplicates back into existing tokens and partials, and simplifies structure — **without changing what the code does**. It exists because AI-assisted flow produces code that is plausible but rarely tidied: duplication rises, refactoring falls, and every new run copies the prior art it finds. A recurring, bounded cleanup pass is the counterweight.

The Skill is a tidying pass, not a redesign. It runs in the main chat by design (`agent-routing` Rule, deliberately not routed): every non-mechanical change is a per-finding decision of the user, and the run ends in the standard commit gate. Read-only auditing of a large scope may be delegated to generic worker subagents (see Step 2). CSS/SCSS, docs, and ledger writes stay in the main chat; child-theme PHP writes follow the `wst-php-authoring-route` Rule and are executed by the `wst-shortcode-implementer` runner as an apply-only step with the exact accepted finding list (see Step 5).

The target user is a frontend or design colleague. Communicate in German for all user-facing steps; keep commands, file names, selectors, and token names in their original language. Every decision shows the finding, the proposed change, the proof mode, and the risk. End each pass with `Erledigt: <result>` or `Offen: <open point> - nächster Schritt: <action>`.

## Modes

| Mode | Trigger | Scope |
|---|---|---|
| `post-run` | Directly after a Section, CPT, ticket, or content run in the same session, or `/code-cleanup` with uncommitted changes present | The files that run touched: `git status --short` plus `git diff --name-only HEAD`, intersected with the editable areas |
| `recurring` | `/code-cleanup` on the team's cleanup rhythm (default: weekly, ≤ 60 minutes) | Everything changed since the last `cleanup/<date>` tag (`git diff --name-only --diff-filter=ACMR cleanup/<last>..HEAD -- themes/<child-theme>/`), plus the top-3 hotspots of the last 90 days |
| `scoped` | `/code-cleanup <section|cpt|file|folder>` | Exactly the named files (a Section = its template, partials, CSS file, and work record) |

Without a `cleanup/` tag the recurring scope falls back to the last 30 days of history (`git log --since=30.days --name-only`). Ask when the mode is ambiguous; never widen the scope silently.

## Inputs

Read before any audit:

- `PROJECT-CONTEXT.md`: child theme path, style loader and style paths, WST template path, working branch (and the legacy state `Working branch: master — user commits`), the `cleanup_tooling` and `cleanup_hook` markers (see `reference/tooling.md`), breakpoints and QA viewport rungs, the docs layer location.
- The project conventions, in this precedence: `docs/coding-standard/<language>.md` (generated by `auto-docs` from the project's real code) → the bundled Rules (`css-guideline`, `wordpress-brand-tokens`, `wst-conditional-nesting`, `wst-php-authoring-route`, `acf-local-json`, `headline-filling`, `file-edit-boundary`, `webroot-safety`) → the WordPress coding standards as the default where both are silent. A documented project deviation from the WordPress handbook (for example short array syntax or non-Yoda comparisons) is a convention, not a finding. When `docs/coding-standard/` is missing, say so, run `auto-docs coding-standard` first or continue with the Rules only and record the gap in the ledger.
- `docs/cleanup-log.md` (the ledger, template in `templates/cleanup-log.md`): deferred findings from earlier runs, recurring patterns, the last tag.
- The `git status --short` baseline of this run (Working Tree Discipline, `deploy-and-branches` Rule): anything on the baseline that the run did not create is pre-existing user work — never staged, never reverted, reported by path.
- The bundled `reference/criteria-catalog.md` (what to look for, per pass and per file type, with auto/judgment and safe/confirm tags) and `reference/tooling.md` (optional linters, configs, hooks, recurrence options).

Do not invent conventions, token names, prefixes, or breakpoints. When a convention is not readable from the docs layer, the Rules, or the code itself, ask or record it as an open convention — do not enforce a guess.

## Hard Rules

These hold in every mode and every pass:

1. **Behavior is preserved.** Rendered HTML, computed styles at every QA rung, field values, hook order, and error behavior stay the same. A change the user thinks is "better behavior" is a ticket, not a cleanup. When a proof diff shows a change, revert the pass.
2. **One pass at a time, safest first, verified and committed before the next.** Never mix passes in one commit; never jump ahead.
3. **Scope is locked.** Only files on the scope list are edited. Findings outside the scope are listed under `Außerhalb des Scopes` in the report, never fixed as a drive-by. The run ends with `git diff --stat` against the scope list.
4. **When in doubt, skip — never guess.** A finding without a `file:line` citation is not reported. A deletion without proof is a candidate, not a change.
5. **Never in this Skill:** renames of `wso-` CSS hooks, ACF field names or keys, function or hook names, shortcode attributes, or file names (all break consumers — they are a planned change with a migration); file moves; new abstractions, helpers, or dependencies; `!important` shuffles to win a cascade; structural ACF changes (audit only, see Pass 4); edits to `functions.php` (forbidden) or `theme-functions.php` / the bridge block in `js-snippets.php` without the explicit confirmation the `file-edit-boundary` Rule requires; anything on the default off-limits list of that Rule.
6. **Budgets.** Default: at most 5 applied judgment findings (Passes 4–6) per run, at most 60 minutes; mechanical passes (1–2) have no finding cap but stay inside the scope. The rest goes to the ledger as `deferred`. The user can raise the budget at intake.
7. **Not before a deploy, not mid-feature.** A cleanup pass does not run while a Section or ticket is half-finished in the working tree, and it does not run into a push the user is about to make. Finish or park the work first.

## Workflow

```text
- [ ] 0. Intake: mode, scope, budget, commit mandate, git baseline
- [ ] 1. Scope list (and hotspots in recurring mode)
- [ ] 2. Audit, read-only: tooling ladder, then agent checks per criteria catalog
- [ ] 3. Findings board (German), grouped by pass
- [ ] 4. Decisions per pass (recommended answer first)
- [ ] 5. Apply pass by pass: proof baseline -> change -> verify -> scope check -> commit
- [ ] 6. Close: deploy hand-over, bridge check, tag, ledger, recurring-pattern proposal
```

### 0. Intake

Ask in one message, with recommended answers:

- **Modus** (`post-run` / `recurring` / `scoped`) — recommended from the situation (uncommitted changes present → `post-run`).
- **Budget** — default 5 judgment findings, 60 minutes.
- **Cleanup-Commit-Mandat** — "Darf ich die Pass-Commits dieses Laufs ohne einzelne Rückfrage setzen (nur `cleanup(<pass>): …`-Commits, nur dieser Lauf, nie ein Push)?" Default **nein**. This is the scoped standing mandate the `deploy-and-branches` Rule allows a Skill to ask for; it covers only the pass commits of this run. Without it, every pass commit is proposed individually. In the legacy state `Working branch: master — user commits`, the agent only prepares commits regardless of the answer.

Take the `git status --short` baseline and confirm the working tree carries no half-finished feature work (Hard Rule 7).

### 1. Scope List

Build the list per the mode table, then filter to the editable areas of the `file-edit-boundary` Rule (child theme minus `functions.php`, `docs/`, `.cursor/`; never plugin folders, parent theme, uploads, generated files). Group by file type: PHP templates/partials, CSS/SCSS, theme snippets (`theme-functions.php`, `js-snippets.php` — audit yes, edit only with the Rule's confirmation), ACF JSON (audit only), other.

Recurring mode adds the hotspots — the files changed most often in the last 90 days — because churn is where duplication and drift accumulate:

```powershell
git log --since=90.days --name-only --pretty=format: -- "themes/<child-theme>/" |
  Where-Object { $_ } | Group-Object | Sort-Object Count -Descending | Select-Object -First 3
```

Show the scope list before auditing. Files the user removes from the list are recorded as `ausgeklammert` in the ledger.

### 2. Audit (Read-Only)

Two layers, in this order:

1. **Tooling ladder.** When `PROJECT-CONTEXT.md` records `cleanup_tooling` and the binaries exist (`vendor/bin/phpcs`, `node_modules/.bin/stylelint`, `editorconfig-checker`, `acf-lint`), run them on the scope list in **report mode** (`phpcs`, `stylelint` without `--fix`) and parse the output; every hit becomes a finding tagged `[auto]`. Do not install tooling inside a cleanup run — the opt-in setup is its own step (`reference/tooling.md`), confirmed by the user and recorded in `PROJECT-CONTEXT.md`. Without tooling, all checks run as agent checks.
2. **Agent checks** per `reference/criteria-catalog.md`: the per-pass criteria for PHP templates, CSS/SCSS, snippets, and ACF JSON, plus the AI-code smell list. Every finding needs `file:line`, the criterion, and the proposed change. For duplication findings, search the theme for the existing token, utility, or partial the code should reuse before proposing anything (the deletion ladder in Pass 5).

When the scope exceeds roughly 15 files, delegate the agent checks to read-only worker subagents — one worker per file group, prompts self-contained per the `agent-routing` orchestration practices (scope list, catalog path, the fixed finding line format below, Working Tree Discipline, no writes, no commits). The main chat merges and deduplicates; it reads no large files itself.

Finding line format (workers and main chat alike):

```text
<pass> | <file>:<line> | <criterion-id> | <tags: auto|judgment, safe|confirm> | <finding> | <proposed change> | <proof mode>
```

### 3. Findings Board

Present the board in German, grouped by pass, each row: `ID`, `Datei:Zeile`, `Befund`, `Vorschlag`, `Tags`, `Beweis` (which proof mode closes it), and for Pass 5 the reuse target that already exists. Add three closing blocks: `Außerhalb des Scopes` (seen, not touched), `Kandidaten ohne Beweis` (deletions that need coverage or a render proof first), and `Wiederkehrend` (a finding already in the ledger from a previous run, with its count). Cap the board at the budget plus the deferred list; do not dump every nit — report the count and defer.

### 4. Decisions Per Pass

Ask once per pass with a recommended answer: `alle safe-Befunde anwenden` (recommended for Passes 1–3 when the diff is mechanical), `einzeln entscheiden`, or `überspringen`. Findings tagged `[confirm]` are always decided individually. Record every decision (`angewendet`, `abgelehnt: <reason>`, `deferred`) — the ledger needs them.

### 5. Apply, Pass By Pass

For each pass with accepted findings:

1. **Proof baseline** for the affected surfaces (see Proof Without Tests). Nothing is edited before the baseline exists.
2. **Change** exactly the accepted findings. Mechanical passes may use the project's fixers (`phpcbf`, `stylelint --fix`) on the scope files only; review the resulting diff before continuing. **PHP files** (`themes/<child-theme>/**/*.php`) are never edited by the main chat (`wst-php-authoring-route` Rule): spawn the `wst-shortcode-implementer` runner once per pass with a self-contained apply-only prompt — the accepted finding lines for that pass verbatim, the write scope (exactly those PHP files), the instruction that `phpcbf` on those files counts as its write, "no other edits, no renames, no new files, no commits, no pushes", and the Working Tree Discipline. The runner returns its diff summary; the main chat reviews the diff, verifies, and commits. If the runner is unavailable, the PHP findings of that pass go to the ledger as `deferred`, not to the main chat's editor.
3. **Verify**: re-run the tooling on the touched files (no new hits), take the after-proof, compare. A diff means revert that finding and record `zurückgenommen: <reason>`.
4. **Scope check**: `git diff --stat` shows only scope files. Anything else is investigated and reported, never silently kept or discarded.
5. **Commit** the pass: `cleanup(<pass>): <what>` with the `Made with: SmartFlow` trailer — through the mandate from intake or an individual proposal (files, summary, message). One pass, one commit, so a single `git revert` undoes exactly one concern.

Pass order and content — details, criteria, and examples live in `reference/criteria-catalog.md`:

| Pass | Name | Typical changes | Risk |
|---|---|---|---|
| 1 | **Format** | tabs/spaces, trailing whitespace, final newline, LF, one declaration per line, spacing, closing `?>`, property order where the project orders | none — mechanical |
| 2 | **Leftovers** | debug calls (`var_dump`, `print_r`, `error_log`, `console.log`), commented-out code, unused local variables and parameters, custom properties never consumed by `var()`, unreferenced partials and CSS files (**candidates** until proven) | low — deletions need the reference search or coverage proof |
| 3 | **Comments and filler** | narration comments that restate the code, empty or signature-restating docblocks, placeholder `TODO: implement`, closing-brace labels, LLM filler; keep every "why" comment and every `!important` explanation | low |
| 4 | **Conventions** | `wso-` class pattern, `wso_` ACF prefix, prefixed globals, late escaping on dynamic output, tokens instead of hardcoded palette values, `!important` and specificity budget, consistent media-query direction and documented breakpoints, WST nesting suffixes, file banners, style-loader registration; ACF JSON: **report only** (naming, duplicate keys, clone prefix, empty location, stale `modified`) | medium — most fixes are `[confirm]`; escaping changes need a render proof |
| 5 | **Duplication → reuse** | deletion ladder: delete → reuse an existing token/utility/partial → platform function → simplify in place; incidental look-alikes with different intent stay apart | medium — needs the reuse target and a proof |
| 6 | **Simplification** | guard clauses instead of nesting, remove over-defensive checks on guaranteed values, drop single-use wrappers and pass-through helpers, split long boolean chains; clarity over brevity | highest — one finding at a time, every one `[confirm]` with proof |

A finding that turns out to need a real restyle, a template change with new output, or an ACF structural change is not a cleanup: route it to `frontend-section-qa`, `wst-section-workflow`, or `wst-new-post-type` and record the route in the ledger.

### 6. Close

1. **Deploy hand-over.** Cleanup commits touch the child theme, so they reach the server through the standard chain: HARD STOP after the last pass commit, hand over with the commit hashes and what the deploy will deliver; the user pushes. After the push, verify `deployed_commit` over the status bridge per the `status-bridge` Rule (bounded retries) and run one served spot check of the proof surfaces. Until then the result is `implementation pass, deployed verification pending`.
2. **Tag** the run locally: `git tag cleanup/<YYYY-MM-DD>` on the last pass commit — the next recurring run's scope anchor. Tags are local until the user pushes them; that is fine, the tag never deploys.
3. **Ledger.** Append the run to `docs/cleanup-log.md` per the template: mode, scope size, per-pass counts (applied / rejected / deferred / reverted), commit hashes, deferred findings with their criterion, and the `Wiederkehrend` counts. `docs/` never reaches the server; a docs-only change needs no deploy.
4. **Recurring-pattern proposal.** A finding that appears in three runs (or three files in one run) is a convention gap, not a cleanup item: propose the sentence for `docs/coding-standard/<language>.md` (and, when it is reusable across projects, a `smartflow-feedback` Skill/Rule proposal). The user decides; nothing is written to Confluence without a yes.
5. **Report** (German): per pass `Erledigt`/`Offen`, the budget used, the tag, the ledger path, and the hand-over sentence. Release any claimed Playwright browser lock.

## Proof Without Tests

The child-theme repositories carry no test suite, so the behavior lock comes from the rendered result:

- **CSS/SCSS**: Playwright MCP screenshots of every affected surface (the Section's preview URL when the harness is active, otherwise the served page) at the project's QA viewport rungs (`frontend-section-qa-tablet-band` Rule) **before** the change; after the change, inject the new rules into the served page (injection-proof per the `css-guideline` Rule), screenshot again, and compare — plus the computed styles of the primary hooks. A deletion candidate additionally needs the reference search (class used in no template, no script, no WPGB config, no `body_class`/state toggle) or a CSS-coverage result across the full rung ladder and states; coverage alone never deletes a state class such as `.is-open`.
- **PHP templates and partials**: the rendered HTML of the affected Section or single (preview URL or served page), normalized (nonces, IDs, timestamps stripped), before and after; the diff must be empty. Escaping changes are the exception that may legitimately alter output — then the before/after diff is shown to the user and confirmed, never assumed harmless.
- **Snippets**: the same HTML snapshot on a page that exercises the snippet; for hook-registered code additionally the hook still fires (visible effect on the page).
- **ACF JSON**: no writes in this Skill, so no proof needed; findings are handed to the WST workflows.

Browser availability and, in workspaces with parallel servers, the claim/release protocol follow the `playwright-browser-claim` Rule. Any proof that cannot be taken (surface not reachable, browser unavailable) blocks that finding — it becomes `deferred: kein Beweis möglich`, never an unproven change.

## Recurrence

The pass stays recurring through the team's rhythm, not through an unattended scheduler — every mechanism that runs unattended in the cloud pushes branches or opens PRs, which the `deploy-and-branches` Rule forbids. The layers, from continuous to planned (details and configs in `reference/tooling.md`):

1. **Post-run**: after every Section, CPT, ticket, or content run, offer `code-cleanup post-run` on the touched files in one sentence. This is the cheapest and tightest loop.
2. **Optional pre-commit check**: a staged-files-only lint hook (report or fix on the touched files) chained with the existing `.githooks/pre-commit` ACF pull hook; opt-in, recorded as `cleanup_hook` in `PROJECT-CONTEXT.md`.
3. **Weekly recurring run**: a calendar reminder; the colleague runs `/code-cleanup` in recurring mode, bounded by the budget.
4. **Not recommended**: `/loop` (session-bound), cloud Automations for applying changes (push conflict; report-only posting is acceptable).

## Stop Conditions

Stop and ask before or when:

- The working tree carries half-finished feature work or the user is about to push.
- A proof surface is unreachable or the browser is unavailable (defer, do not guess).
- A pass diff is larger than expected (more than roughly 300 changed lines in one pass) — split or defer.
- A finding needs a rename, a file move, a new abstraction, an ACF structural change, or an edit to a confirmation-gated file.
- The same finding was reverted twice in this run (`zurückgenommen`) — the code is not as understood; escalate instead of a third attempt.
- Any commit without the run's mandate, and every push (the agent never pushes).

## Scope Boundaries

This Skill tidies existing child-theme code without changing behavior. It does not build or restyle Sections (`frontend-section-qa`, `wst-section-workflow`), does not create or remodel CPTs (`wst-new-post-type`), does not write ACF JSON (`acf-local-json` Rule; findings are handed over), does not reconcile global theme values with the design (`project-css-setup`), does not document (`auto-docs` — though it consumes `docs/coding-standard/` and proposes additions to it), and does not clean the workspace itself (drifted plugin copies, retained work records — a separate maintainer concern). It never installs tooling silently, never runs unattended, and never pushes.

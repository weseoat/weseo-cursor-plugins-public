# SmartFlow 1.2.0-beta.1

The established rendering path for WST CPT detail pages is now bundled knowledge: single partials render only through a Smart Template assignment (partial plus one `[wst_include]` in the Smart Template's top-level code editor), never through the WordPress template hierarchy. `wst-new-post-type` carries the path, the role split, and the ACF shortcode pitfall; `cpt-frontend-qa` treats generic theme output on a single URL as a pending admin step instead of a debugging target.

Source: a real `wso_job` foundation run in the playground project where the agent did not know the path and burned rounds on template-hierarchy assumptions and `theme-functions.php` workaround proposals (`plugin-feedback/cpt-single-template-rendering.md`).

## Changed

- `wst-new-post-type` step 4.7 documents how the single partial actually renders: WST projects have no `single.php`/`page.php` in the child theme, so the partial under `post-types/<resource>/singles/` is never auto-discovered. The user creates a Smart Template (post type `smart_template`, category "Post Types"), assigns it under Smart Template → Settings → Post Types → <CPT> → Template Assignment, and pastes exactly one agent-delivered include into the enabled **top-level code editor** (Flexible Content stays empty; never a code-editor Section): `[wst_include template="post-types/<resource>/singles/<resource>-single.php"]`. Only then does WST replace the single output.
- New hard stop rule in `wst-new-post-type`: never self-solve the rendering — no `single-<resource>.php`/`page.php` theme files, no `template_include` workaround in `theme-functions.php`, no auto-discovery assumption. The admin steps go to the user as a Smart Template apply-spec (new shape in `reference.md`); the foundation checklist and the verification section carry the new step and the single-URL expectation.
- Read-verification documented: `smart_template` posts are not REST-exposed (`show_in_rest = false`); the agent read-verifies the assignment over XML-RPC (`wp.getPost`, Application Password) via the metas `smart_template_code_editor_enabled` / `smart_template_code_editor_content`. Smart Template post ID and assignment status land in the work record and `PROJECT-CONTEXT.md`.
- ACF shortcode pitfall in the include context anchored in SKILL, reference, and examples: generic `[wst_acf field='…']` resolves empty inside the single partial (ACF strict resolution over `get_field_object()`) — CPT single partials use typed shortcodes (`[wst_acf_text]`, `[wst_acf_wysiwyg]`, …) or the `field_…` key; `[wst_post_*]` and `[wst_if]` work normally. The examples single shell now shows the typed pattern.
- `cpt-frontend-qa`: a single URL that renders only the generic theme output (expected `.wso-<resource>-single` hook absent) means the Smart Template assignment is pending — recorded as `injection proof: blocked: smart-template-assignment-pending` for the single surface with a hand-over to the user, never a CSS or template debugging round; the other surfaces continue.

## Notes

- The rendering mechanism (WST's `template_include`/`the_content` replacement) is WST runtime behavior; the plugin documents the workflow around it, not the plugin internals.
- Reference run: playground project, CPT `wso_job`, Smart Template post 2060, partial `post-types/job/singles/job-single.php`, documented with all dead ends in the project's `docs/post-types/job.md`.

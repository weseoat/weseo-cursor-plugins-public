# SmartFlow 0.9.0-beta.1

Wave 2 of the SmartFlow rework: the three remaining workflow Skills (`figma-page-builder`, `jira-ticket-workflow`, `jira-batch-workflow`) and the sixth agent (`jira-ticket-runner`) are ported from the frozen `Tests/` prototype and adapted to the SmartFlow model — no server shell, REST content writes, status-bridge flushes, docs-layer work records, commit-and-hand-over, and project values in `PROJECT-CONTEXT.md`. The three deterministic QA tools from the prototype (`gate.mjs`, `compare-png.mjs`, `sweep-plan.mjs`) are deliberately not ported (decision confirmed 2026-08-25); their evidence discipline lives on as prose in the frontend QA Skills.

## Added

- `figma-page-builder` Skill: build or remodel a WordPress/WST page from a Figma page frame by reusing the project's existing Flexible Content Sections, WPGB surfaces, media, and global elements. Parallel Figma/codebase discovery (`cpt-figma-analyst` + `explore`, models per `agent-routing`), a binding ordered page map with surface classification (`global`, `existing-wst`, `existing-wpgb`, `content-only`, `structural-gap`), and structural plus visual acceptance. Adapted from the prototype: content population goes over REST per the `content` Skill and `wordpress-content-editing` Rule (backup under `tmp/`, full FC array round-trip, layout fingerprint guard) instead of WP-CLI `eval-file`; cache flushes go through the status bridge; structural gaps route to `wst-section-workflow` via `wst-shortcode-implementer`; CSS gaps route to the bundled frontend QA Skills; reused surfaces are read from the docs-layer work records instead of legacy handoffs.
- `jira-ticket-workflow` Skill: one WESEO Jira ticket (WP-key) end to end — Atlassian MCP intake with the mandatory screenshot rule (`jira_get_issue_images` as the primary path, Playwright fallback, hard stop instead of blind visual diagnosis), triage/routing table to the bundled Skills and subagents, minimal child-theme fix inside the `file-edit-boundary`, Playwright injection-proof verification with honest proof-mode reporting, German report with approval gate, then one commit per ticket (trailer per `commit-trailer`, never push) and a German Jira solution comment (never a status transition). Adapted from the prototype: the legacy Remote-SSH server environment is gone — the local SmartFlow workspace is the only environment, source-served proof exists only after the user's push plus the bridge `deployed_commit` check; the hardcoded server path, project name, dev URL, and 8-step viewport ladder moved to `PROJECT-CONTEXT.md` reads; handoff reads became docs-layer work-record reads.
- `jira-batch-workflow` Skill: orchestrates a batch of open subtasks (default 10) of one parent task — JQL intake over `statusCategory = "To Do"` only, screenshot-based triage, untracked statusboard under `.cursor/jira-batch/<parent-key>.md`, up to three parallel background `jira-ticket-runner` leaves with file-disjoint write ownership and chain serialization, feedback relay via resume, automatic serialized per-ticket commits in the main chat (never push), final batch review, and Jira solution comments only after the user closes the review. Router and closer only; per-ticket semantics stay in `jira-ticket-workflow`.
- `jira-ticket-runner` agent (`composer-2.5-fast`): thin leaf runner for exactly one direct-fix subtask, executing steps 3–5 of the bundled `jira-ticket-workflow` Skill inside its assigned file group, with the Playwright lock protocol, an emergency brake (`route-back` with reverted partial edits), and the fixed return format including `STATUS: handoff` for context-full continuation.

## Changed

- `agent-routing` Rule: now covers six bundled subagents — `jira-ticket-runner` joins the delegation and model routing tables; the background-agent default gains the documented exception for batch runners.

## Notes

- Wave 2 was ported while the three runtime validations from `docs/open-validations.md` (`{{post.id}}` vs `{{post_id}}`, conditional suffix chain, WPGB writability) are still open; none of them blocks these Skills, but the WPGB answer will sharpen the `figma-page-builder` `existing-wpgb` route.
- With this build the porting source `Tests/` is fully consumed: the remaining prototype content (lean CPT workflow skills, five package agents, rules) was already absorbed in wave 1, `Tests/package/` stays archived pilot evidence, and the `.mjs` tools stay unported by decision.
